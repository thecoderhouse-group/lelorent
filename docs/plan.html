1Backend: no separate Node server

Your instinct is right. Next.js Route Handlers and Server Actions are the Node backend. A separate Express service would mean a second deploy, a second cold start, CORS, and duplicated auth — with zero benefit at this scale.

ConcernHandled by
Create / edit / delete listingServer Actions
Search and read pathsReact Server Components hitting Supabase directly; filters live in the URL
Cron, cleanup, webhooksRoute Handlers in app/api/*
Photo bytesBrowser uploads straight to Supabase Storage via signed URLs — never through Vercel

2Firebase vs Supabase

Three reasons, in order of how much they matter here.

Recommendation

Supabase. The deciding factor is not pricing — it is that this app is a filter engine, and Firestore is bad at filter engines.

2.1Your app is a filter engine

You will filter on roughly twelve optional dimensions simultaneously: type, rent range, food preference, pets, tenant type, furnishing, city, locality, amenities, availability date, deposit, gender. In Postgres that is one WHERE clause.

NeedPostgresFirestore
Arbitrary combos of 12 optional filters One query, planner picks the index Needs a composite index per filter combination — combinatorial explosion
Two range filters at once Trivial Supported since 2024, but forces index intersection and scans
Multi-select amenities (“has all of”) text[] @> array[...] with a GIN index One array-contains-any per query, max 30 values, can’t combine two
Full-text on locality and title Built-in tsvector Not supported — bolt on Algolia or Typesense
Radius search (“within 3 km”) PostGIS ST_DWithin Geohash prefix hack, done by hand
Sort by rent, then filter Free Sort field must appear in every index
“142 results found” count(*) Costs one read per counted document

This alone decides it.

2.2Firebase Storage is no longer free for new projects

Blocker

Cloud Storage for Firebase and Cloud Functions both require the Blaze pay-as-you-go plan on projects created since late 2024. Photos are core to your product, so “Firebase free tier” does not really exist for this app — you would be attaching a credit card on day one.

4.1The 4-photo cap, enforced in the database

Don’t trust the UI for “max 4 photos”.

create or replace function enforce_photo_limit() returns trigger language plpgsql as $$
declare n int;
begin
  select count(*) into n from listing_photos where listing_id = new.listing_id;
  if n >= 4 then raise exception 'max 4 photos per listing'; end if;
  return new;
end $$;

create trigger photo_limit before insert on listing_photos
  for each row execute function enforce_photo_limit();

-- keep listings.photo_count in sync so search results don't need a join
create or replace function sync_photo_count() returns trigger language plpgsql as $$
begin
  update listings set photo_count = (
    select count(*) from listing_photos
    where listing_id = coalesce(new.listing_id, old.listing_id)
  ) where id = coalesce(new.listing_id, old.listing_id);
  return null;
end $$;

create trigger photo_count_sync after insert or delete on listing_photos
  for each row execute function sync_photo_count();

create index listings_browse_idx on listings (status, city, rent)        where status='PUBLISHED';

create index on listings (owner_id, status);
create index on listing_photos (listing_id, position);

Partial indexes on status='PUBLISHED' keep them small — draft and rented rows never bloat the index.

4.3Row-level security

Turn RLS on for every table.

  • listings — anyone can select rows where status='PUBLISHED'; the owner can select, insert, update, and delete their own.
  • Private fields — address_line and owner contact must not be in the public select path. Expose search results through a listings_public view with an explicit column list, and reveal contact only via an authenticated RPC that also logs the reveal.
  • listing_photos — select allowed if the parent listing is visible; write only by the owner.
  • Storage policies mirror this — the write path must start with listings/{id}/ where the caller owns {id}.

5Photo pipeline — max 4 per listing

Principle

Compress in the browser, upload the compressed bytes directly to Supabase Storage via signed URLs. Originals never touch your server — zero Vercel function time, zero Vercel bandwidth, and the free tier only ever stores the small version.

5.1Three artifacts per photo

VariantLongest edgeQualityTargetUsed on
card640 px0.72~30 KBSearch results grid
full1600 px0.80~180 KBDetail page and lightbox
blur20 px0.5~400 BInlined base64 LQIP, stored in the DB row, not Storage
 
import imageCompression from 'browser-image-compression';

const opts = { useWebWorker: true, fileType: 'image/webp' as const };
const card = await imageCompression(file, { ...opts, maxWidthOrHeight: 640,  initialQuality: 0.72 });
const full = await imageCompression(file, { ...opts, maxWidthOrHeight: 1600, initialQuality: 0.80 });

Upload with a long cache header. You already produced the exact display size, so next/image re-optimization would only burn Vercel’s transformation quota — render these with <Image unoptimized> or a plain <img>. 

await supabase.storage.from('listing-photos')
  .upload(path, blob, { contentType: 'image/webp', cacheControl: '31536000', upsert: true });

5.2Four things that will actually bite you

  • HEIC from iPhones. Photos picked from the iOS Files app arrive as .heic, which Chrome and Firefox cannot decode to a canvas — compression silently fails. Detect the type and route through heic2any before compressing. The iOS camera picker usually hands over JPEG, so this only affects a subset of users, which is exactly what makes it easy to miss in testing.
  • EXIF GPS leaks the exact flat address. browser-image-compression re-encodes via canvas, which drops EXIF — but verify it on a real geotagged photo, and never echo address_line from the public view.
  • EXIF orientation. Apply rotation before stripping metadata, or portrait photos upload sideways. Let the library handle it, then confirm with a photo from a phone.
  • Validate server-side too. Check content type and byte length in the Server Action before inserting the listing_photos row. A signed upload URL is a write primitive — treat anything the client claims about the file as untrusted.

Reject inputs over roughly 25 MB before compressing, cap at four files per selection, and show per-file progress.

5.3Upload flow — avoids orphaned files

  1. User completes step 1 of the wizard. A Server Action inserts a DRAFT listing and returns the listing_id.
  2. Client compresses each photo into card, full, and blur variants.
  3. Client requests signed upload URLs for listings/{listing_id}/....
  4. Browser PUTs bytes straight to Supabase Storage, with a progress bar per file.
  5. Server Action inserts the listing_photos rows. The trigger enforces the cap of four.
  6. User drags to reorder. position = 0 is the cover photo shown on search cards.
  7. Final step sets status='PUBLISHED', published_at=now(), and expires_at=now()+60 days.
Nightly cron

One daily Vercel Cron does four jobs: delete DRAFT listings older than 24 hours along with their storage objects, expire listings past expires_at, sweep storage objects with no matching listing_photos row, and keep the Supabase project from auto-pausing.

Search results, 12 cards~360 KB~14,000

Both are comfortable for launch. Levers if you approach the cap, cheapest first:

  1. Lazy-load card images below the fold with loading="lazy"; the blur LQIP covers the gap.
  2. Paginate at 12–20 results using keyset pagination, not offset.
  3. Load the full-size photo only when the lightbox opens — show the card upscaled behind the blur until then.
  4. Put a Cloudflare-proxied custom domain in front of the storage bucket.
  5. Supabase Pro at $25/mo → 250 GB egress.
Do this on day one

Set up usage alerts in the Supabase dashboard. Hitting the storage cap silently fails uploads.

7Search implementation

Filters live in the URL:

/search?city=pune&type=2BHK,3BHK&rent_max=25000&food=VEG_ONLY&pets=1&amenities=lift,parking

Parse, run through Zod, then build one Supabase query. Every filter is conditional; unset filters add no clause.

let q = supabase.from('listings_public')       // view: excludes address_line, owner contact
  .select('id,title,rent,flat_type,locality,city,food_pref,pets_allowed,available_from,cover_card_path,blur_data_url',
          { count: 'exact' })
  .eq('status', 'PUBLISHED');

if (f.city)        q = q.eq('city', f.city);
if (f.types)       q = q.in('flat_type', f.types);
if (f.rentMin)     q = q.gte('rent', f.rentMin);
if (f.rentMax)     q = q.lte('rent', f.rentMax);
if (f.food)        q = q.in('food_pref', f.food);
if (f.pets)        q = q.eq('pets_allowed', true);
if (f.furnishing)  q = q.in('furnishing', f.furnishing);
if (f.amenities)   q = q.contains('amenities', f.amenities);     // GIN, "has ALL of"
if (f.tenant)      q = q.overlaps('tenant_prefs', f.tenant);     // GIN, "has ANY of"
if (f.availBy)     q = q.lte('available_from', f.availBy);
if (f.withPhotos)  q = q.gt('photo_count', 0);
if (f.text)        q = q.textSearch('search_vector', f.text);

q = q.order(sortColumn, { ascending: sortAsc }).range(offset, offset + 19);

Build listings_public as a view that already joins in the cover photo (position = 0), so search never needs a second round-trip for images.

Radius search needs PostGIS ST_DWithin, which PostgREST cannot express — write that one as a search_listings(...) SQL function and call it via .rpc(). Ship the flat version first and add geo in phase 5.

Filter UX

Sidebar on desktop, bottom sheet on mobile. Active filters render as removable chips with a live result count. Debounce the rent slider by about 300 ms. Because state lives in the URL, RSC re-renders handle everything with no client fetch layer.

Two sequencing notes

Ship phase 3 against seed data before building phase 4. The search page is what tells you whether your filter set is actually right, and changing the schema is far cheaper before a form is bound to it.

Test the photo pipeline on a real phone during phase 4, not at the end. HEIC and EXIF orientation are invisible on a desktop dev machine.

9Decisions to make before phase 2

  • 9.1
    Geography. One city or many? Determines whether city is an enum, a lookup table, or free text, and whether you need locality autocomplete. The plan assumes multi-city, with a cities and localities lookup added in phase 3.
  • 9.2
    Contact model. Reveal the phone number after login, or build in-app messaging? Messaging is a whole extra subsystem — Supabase Realtime, notifications. Recommended: gated phone reveal for v1.
  • 9.3
    Who posts. Owners only, or brokers too? Changes moderation, and whether you need a “posted by” badge — one of the most-used filters on Indian rental sites.
  • 9.4
    Listing lifetime. The plan assumes 60-day auto-expiry with a renew prompt, which keeps the free tier from filling with stale listings.
  • 9.5
    Monetization. None in v1 — but if featured listings are coming, add is_featured boolean and featured_until timestamptz in phase 2 rather than migrating later.
  • 9.6
    Is 4 photos enough? Worth revisiting now that video is gone. Rental sites typically allow 8–10, and renters skip listings that don’t show the bathroom and kitchen. At 8 photos you would still fit ~600 listings in the free tier. Keeping the cap at 4 as specified — flagged because the constraint that motivated it no longer applies.
